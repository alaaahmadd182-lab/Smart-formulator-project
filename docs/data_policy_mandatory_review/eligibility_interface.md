# Product eligibility interface (Workstream A → Workstream B)

The file is `reports/mandatory_properties/product_eligibility.csv`. It is generated by
`python tools/mandatory_properties/build_eligibility.py`; to check it without writing, run `--check`.

**Meaning.** `formulation_eligible = true` means only this: every mandatory Tier 1 requirement is met under the
mandatory-data rules of `requirements_version`. It is not a statement of chemical suitability, compatibility or
performance. Products that are not eligible stay in the database and keep all their data.

## Format

- UTF-8, comma-separated, RFC 4180 quoting, `\n` line ends, one header row.
- One row per product folder, sorted by `product_id`.

| Column | Type | Content |
|---|---|---|
| `product_id` | string | The existing stable id: the product folder name in `Products_json` (e.g. `RICHFUL_RF6077`, `RF6602`). |
| `material_class` | enum | `base_oil`, `additive_package` or `additive_component` (the `material_class` key of the JSON). |
| `product_name` | string | `product.product_name` of the Tier 1 (or component `general`) file. |
| `supplier` | string | `product.supplier` of the same file. |
| `tier1_complete` | `true`/`false` | Every mandatory requirement is met. |
| `formulation_eligible` | `true`/`false` | Same as `tier1_complete` in this version. It is a separate column so that later versions can add gates that are not Tier 1. |
| `missing_mandatory_properties` | JSON array of strings | Requirement ids that are not met, e.g. `["ccs", "density"]`. It is empty only when the product is eligible. |
| `eligibility_reasons` | JSON array of strings | One reason per unmet requirement, then notes: an applicability rule used, or an unresolved conflict on a satisfied property. For an eligible product the first item states the rule version. |
| `calculated_mandatory_properties` | JSON array of strings | Requirement ids satisfied by a `Calculated` value that passed a registered reproducibility check. |
| `requirements_version` | string | `mandatory-tier1-2026-11-10`. |
| `source_snapshot_sha256` | hex string | The data snapshot the row was computed from (see below). |

Booleans are lowercase. The three list columns are always valid JSON arrays, so `[]` is never an empty cell.
A row whose requirement or calculation could not be established is never `true`: the reason says why.

## `source_snapshot_sha256`

The snapshot hash is computed in four steps:
1. List every `Products_json/**/*.json` file by its project-relative POSIX path (e.g. `Products_json/Base_oils_json/YUBASE/YUBASE_6/YUBASE_6_tier1.json`).
2. Sort the list by the UTF-8 bytes of the path.
3. For each file, write one line `<sha256 of the exact file bytes><two spaces><path>\n`.
4. Take the SHA-256 of the UTF-8 manifest.

The file bytes depend on the checkout's line-ending conversion: `core.autocrlf=true` rewrites line endings on
checkout. Compare hashes only between checkouts with the same setting, or recompute the hash. A consumer should
reject or recompute eligibility when its own snapshot hash differs from the one in the file.

## Requirement ids (version `mandatory-tier1-2026-11-10`)

Sources: `Smart_Formulator_Minimum_Property_Set.pdf` (slides 2–4), `Property_Glossary.docx`, and `json_templates/`.

### Base oil: Tier 1, "all six required"

| Id | Satisfied when |
|---|---|
| `api_group_chemistry.api_group`, `api_group_chemistry.chemistry` | Both are `Reported` with a value and a source. |
| `kv40`, `kv100` | A point value or a two-sided range, with a unit and a source. |
| `viscosity_index` | A point value or a two-sided range, with a source. A calculated VI needs a registered check; none is registered, because the ASTM D2270 tables are not in the repository. |
| `density` | A value, a unit and a reference temperature (`test_temperature_c`). Specific gravity never substitutes for density. |
| `ccs` | At least one CCS entry with a value, a unit and a test temperature. |

### Additive package: Tier 1, route-defining

| Id | Satisfied when |
|---|---|
| `package_type_application.package_type`, `.intended_service` | Both reported. |
| `performance_claims` | At least one claim with a designation, a claim type and a source. |
| `sae_grades_documented` | At least one grade with a source. |
| `treat_rate_matrix` | At least one entry with a numeric treat rate on a mass basis (wt.%). |
| `permitted_base_oils_restrictions`, `route_selector_restrictions` | Reported blocks with content and a source. |
| `required_co_components` | At least one named co-component with a wt.% dose. |
| `published_formulations` | At least one reported formulation whose ingredients sum to 100.00 wt.% (± 0.005). |

### Additive component: block A for every component, plus subtype blocks

| Id | Satisfied when |
|---|---|
| `function.primary` | Reported. The secondary function is optional. |
| `chemical_family`, `carrier.identity` | Reported. |
| `active_content` | A numeric value or range. |
| `treat_rate` | A numeric value or range on a mass basis (wt.%). |
| `compatibility_restrictions` | A reported block with content. |
| `function_specific_markers.*` | Detergent: `tbn` and `ca\|mg`. ZDDP: `p` and `zn`. Molybdenum: `mo`. Other functions: not applicable (rule CG-6-APPL). If the primary function is missing, applicability cannot be established and the requirement is not met. |
| `vm.*` | A viscosity modifier (by function, chemical family or a `vm.json` file) must meet block B: `polymer_chemistry` (type and form), `active_polymer.wt_pct` and `carrier_identity`, `treat_range_by_sae_grade`, `thickening_response`, `shear_stability`, the five `post_shear_blend_behaviour.*` items, and `dissolution_blend_temperature`. |
| `ppd.*` | A pour point depressant must meet block C in the same way. No PPD exists yet. |

### General checks

- **Statuses.** `Reported` and `Calculated` can satisfy a requirement. `Missing` never does. `Not Required`, `Not Applicable` and `N/A` satisfy a requirement only under an approved applicability rule; none is approved yet. The `Not Required` labels on SHELL_RISELLA_X_415/420/430 cite a "proposed project applicability rule", so they do not satisfy.
- **Zero** is a valid value.
- **A one-sided bound** (`minimum 4.0`, qualifier `Max`, value kind `minimum`) does not satisfy a numeric requirement.
- **A calculated value** satisfies a requirement only through a registered check. The check reproduces the arithmetic from inputs stated in `calculation_note`, and requires the inputs to have a source and the response entry to state its reference oil, dose and method. Registered checks: ΔKV100 (thickening response) and shear viscosity loss. No statistical imputation is ever used.

The interpretations I-1 … I-8 in `tools/mandatory_properties/requirements.py`, listed in
`missing_mandatory_properties.md`, are project readings that need reviewer confirmation.

## Companion files

- `reports/mandatory_properties/missing_mandatory_properties.csv`: one row per unmet requirement, with columns
  `product_id, material_class, product_name, requirement, reason, calculated_value_rejected`.
- `reports/mandatory_properties/missing_mandatory_properties.md`: counts by class, by requirement, and the number of unmet
  requirements per product.

## Stability promise to Workstream B

- The column names, their order and the encodings above are fixed for `requirements_version` values that start with `mandatory-tier1-`.
- A change of meaning gets a new `requirements_version`.
- New requirement ids may appear in the list columns; consumers should not assume a closed set.
